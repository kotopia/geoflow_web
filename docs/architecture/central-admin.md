# 중앙 사용자·그룹 관리

## 목적과 원본

중앙 DB의 `users`, `groups`가 계정과 테넌트의 원본이다. 접속 설정은 기존
`GroupDBConfig → Secrets Manager` 경로를 유지한다. 테넌트 업무 DB에는 이 설정을 복제하지 않는다.

## 삭제 항목 표시

- 사용자·그룹 목록은 삭제 항목을 기본 숨기고 `모두 보기(삭제 포함)`로 표시한다.
- 비활성·승인 대기 계정은 삭제가 아니므로 계속 표시한다.
- 그룹은 기존 `groups.deleted_at`을 사용한다. 컬럼이 없는 기존 중앙 DB에서는
  삭제로 추정하지 않는다. 그룹 삭제·복구 절차 자체는 이번 변경 대상이 아니다.
- 사용자 익명화 시 `users.deleted_at`을 같은 삭제 트랜잭션에서 기록한다.
  실제 삭제된 사용자는 모두 보기에도 나타나지 않는다. 익명화된 사용자는
  `삭제된 사용자`로 표시하며, 감사 이력과 기존 개인정보 삭제 서비스는 유지한다.
- migration 0007은 기존 삭제 서비스가 생성한 정확한 UUID 익명 이메일 형식,
  비활성/미인증/비관리자, 비어 있는 이름, 사용 불가 비밀번호, 그룹 소속 없음이
  모두 일치할 때만 `updated_at`을 삭제 시각의 대용값으로 이관한다.
  런타임 목록은 이메일 문자열로 삭제를 판정하지 않는다.

## 그룹별 서비스 메뉴 표시

그룹 수정 화면에서 입찰·GIS·파이낸스를 각각 선택한다. 중앙 전용
`group_service_menu_settings`에 그룹당 한 행으로 저장한다. 기존 모델에 메뉴
설정 필드가 없으며 DB 접속 설정과 의미가 달라 독립된 작은 테이블을 사용한다.
행이 없으면 세 메뉴 모두 표시한다. 신규 그룹도 같은 기본값이다.

공통 사이드바는 그룹 설정과 기존 사용자별 표시 조건을 함께 적용한다.
현재 확인된 다른 업무 화면의 서비스 진입 링크는 이 사이드바에 모여 있다.
서비스 내부 화면의 탐색 링크 및 직접 URL 접속은 기존 기능을 유지한다.
설정은 세션에 저장하지 않고 현재 요청의 확정된 테넌트·그룹 문맥에서 읽으므로
중앙 변경과 그룹 전환은 다음 페이지 요청에 반영된다.

**이 설정은 이용 차단이나 권한 부여가 아니다.** 재무 조회는 `finance.view`,
변경은 `finance.view + finance.edit`를 계속 요구한다. 계약/프로젝트의 재무
이벤트·첨부·캘린더에도 기존 재무 권한이 유지된다. 메뉴 숨김으로 재무 이벤트를
추가로 숨기거나 권한을 회수하지 않는다. 업무 데이터 삭제, 사용자 역할 변경,
QGIS/QField 서버 접근 제한도 수행하지 않는다.

권한 기준: [Finance 권한 분리](../finance/finance-permission-rollout.md).
실제 서비스 접근 차단은 별도 범위이며 같은 설정을 권한으로 오인하지 않는다.

## 적용·되돌리기 및 현재 상태

PR #403으로 구현했으며, 2026-10-13 중앙 0007 적용과 코드 배포 승인을 받았다.
운영 적용 결과는 실제 배포 실행의 성공 여부로 구분한다.
운영 적용 전 중앙 `control.0007_admin_visibility`의 계획과 기존 그룹 삭제 컬럼을
읽기 전용으로 확인하고, 승인된 중앙 migration 후 코드 배포를 수행한다.
테넌트 migration은 없다. 코드만 먼저 배포되면 서비스 메뉴 설정은 비활성화되고
기존 메뉴와 사용자 목록을 유지한다. 사용자 삭제 표시는 migration 이후 완성된다.
이 호환 처리는 모든 운영 중앙 DB에 0007 적용을 확인한 후 제거할 수 있다.

코드 롤백 시 새 테이블·삭제 표시를 보존한다. 0007은 감사 표시를 지우지 않도록
역방향 DDL을 제공하지 않는다. 구버전으로 롤백한 기간의 신규 익명화 기록은
재배포 전에 동일한 보수적 조건으로 추가 이관 여부를 확인해야 한다.

### 승인된 활성화 경로

기존 production Environment 보호, 정확한 release SHA, SSH 검증 및 코드 롤백을
유지한 workboard 배포에서 `activate_admin_visibility --apply`를 재시작 전에 실행한다.
기본 실행은 계획만 확인한다. 적용은 검토된 migration 파일 해시와 중앙 DB를 확인하고,
미적용 계획이 정확히 control.0007 하나이거나 이미 적용된 경우만 허용한다.
다른 선행 migration이 필요하면 자동 적용하지 않고 중단한다. 중앙 트랜잭션 잠금 아래
스키마·이관·migration 기록을 함께 적용하고 Finance 역할 매핑 불변성을 확인한다.
CI의 임시 PostgreSQL에서 미적용 상태의 적용, 재실행, 이관/설정 저장을 검증한다.


## 테넌트 직원 등록

중앙 사용자 상세의 `테넌트 직원으로 등록`은 가입 완료 계정의 테넌트·역할과
직원 이름(미입력 시 중앙 가입 이름)을 받아 직원 생성/연결과 멤버십 부여를 수행한다.
기존 `그룹/역할 지정`은 권한만 변경한다. 외부 협업자에게 직원 등록을 강제하지 않는다.
테넌트에서 직원을 먼저 만들고 권한을 요청하거나, 중앙에서 등록한 뒤 테넌트
관리자가 기존 권한 요청 기능으로 변경을 요청할 수 있다. 권한 요청은 중앙 승인 전
실제 권한을 변경하지 않는다.

- 중앙 `users`와 `user_group_map`이 계정·권한 원본, 테넌트 `hr.employee_profile`이 인사 원본이다.
- 중앙 관리자만 POST+CSRF로 실행한다. 승인·인증·비밀번호 상태, 활성 그룹/역할을
  기존 `assign_group_role`의 잠금/검증으로 재확인한다. 중앙 전용 역할은 직원 등록에 사용할 수 없다.
- 테넌트 연결은 기존 `GroupDBConfig → Secrets Manager → tenant_cursor`를 재사용한다.
  요청이 DB alias/접속정보를 지정하거나 관리자 세션의 테넌트를 차용하지 않는다.
- UUID 또는 이메일로 후보를 확인하며 기존 직원은 `central_user_id`만 연결한다.
  이름·부서·직급·재직상태·배치 이력을 덮어쓰지 않는다. 신규 직원은 기존 직원
  등록과 같은 `재직` 기본값을 사용한다. 직원 `role_code`를 권한 캐시로 복제하지 않는다.
- 중복 후보, 다른 계정 연결, UUID에 연결된 직원의 이메일 불일치, 삭제된 직원은 차단한다.
  삭제 복구는 테넌트의 기존 권한/절차로 한다. 등록 중 짧은 테이블 쓰기 잠금으로
  중앙 재시도와 테넌트 직접 등록의 경합을 직렬화한다. 테넌트 직접 등록도 같은
  트랜잭션/잠금 안에서 중복 확인 후 저장한다.

### 두 DB 저장과 감사

중앙 migration `0010_tenant_employee_registrations`는 시도별 사용자·그룹·역할·실행자,
상태·시각·완료 직원 UUID를 저장한다. 이름/이메일/자격 등 인사 원본은 복제하지 않는다.
기존 합류 요청은 요청자의 권한 변경 대기/승인 상태를 나타내므로 직원 생성 시도와
부분 저장 복구 기록으로 재사용하지 않는다. 테넌트 스키마 변경은 없다.

먼저 `pending` 시도를 중앙에 확정하고, 중앙 계정·그룹·역할 잠금 아래 테넌트 직원을
생성/연결해 커밋한다. 그 다음 중앙 멤버십과 시도의 `completed`를 같은 중앙 트랜잭션에
커밋한다. 두 DB를 하나의 원자적 트랜잭션이라고 간주하지 않는다.

테넌트 오류는 중앙 역할 변경을 롤백한다. 테넌트 커밋 후 중앙 실패/프로세스 중단 시
직원만 남을 수 있으며 `failed`/`pending`으로 남고 완료를 표시하지 않는다. 기존에 부여된
권한은 유지되며 새 역할을 성공했다고 안내하지 않는다. 같은 계정·테넌트·역할로 다시
등록하면 기존 직원을 재사용한다. 커밋 응답이 유실된 경우도 같은 방식으로 재확인한다.
이력 화면의 완료는 등록 당시 결과이며 이후 인사/권한 변경 상태를 보장하지 않는다.

### 코드·적용 상태

- `control/views_user_assignment.py`: 공통 역할 부여, 중앙 직원 등록 POST
- `control/services/tenant_employee_registration.py`: 명시적 등록·연결, 감사와 재시도
- `control/views_users_admin.py`, `templates/control/users_detail_admin.html`: 버튼과 최근 등록 결과
- 기존 `geoflow_ops/views_employee_role_request.py` → `tenant_role_request_service` → 중앙 합류 요청 승인 경로 유지

로컬 구현과 관련 회귀검사 76개가 통과했다. 기존 승인 서비스의 실행자 누락 검사도
`None`을 명시적으로 거부하도록 보완했다. 별도 중앙/테넌트 PostgreSQL의 실제 저장,
부분 실패 후 재시도, 테넌트 역할 요청→중앙 승인은 [PR #452의 격리 CI](https://github.com/kotopia/geoflow_web/actions/runs/41406865462)에서 통과했다.
중앙 등록과 테넌트 직접 등록 경합도 별도 회귀검사로 포함한다. 운영 미적용이며
중앙 0010 migration 적용이 필요하다.
미적용 시 중앙 사용자 상세는 기존 기능을 유지하고 새 등록 버튼은 준비 중으로 표시한다.
기존 사용자의 일괄 등록/데이터 보정은 하지 않는다. 되돌릴 때 코드를 이전 버전으로
되돌려도 감사 테이블과 이미 생성된 직원·멤버십은 보존한다. 운영 migration/배포는 별도 승인 대상이다.
