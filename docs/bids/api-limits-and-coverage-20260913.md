## 이번 보완

이전 코드는 totalCount까지 루프를 돌지만 all() 도중 중단되면 수신 페이지를 메모리에서 잃었다.
이번에는 기존 CollectionJob.progress JSON에 요청별 페이지·수량·원본행을 임시 보관하고
성공 응답마다 저장한다. 고정된 미완료 구간/같은 요청은 마지막 저장 페이지 다음부터 재개한다.
상세 요청에도 적용하므로 공고의 지역만 받고 예산이 끝나도 지역 요청을 반복하지 않는다.
페이지 정보 불일치, totalCount 변동, 반복 페이지, 빈 중간 페이지는 실패 처리한다.
일관성이 깨진 해당 요청 캐시는 폐기해 다시 조회하되 저장된 공고와 완료 커서는 보존한다.
구간 성공 후 임시 원본 캐시는 제거하고 최근 구간의 totalCount/페이지별 수신수/중복수를 남긴다.
이는 최근 구간의 증거이며 과거 2년 전체 감사 원장을 소급 생성한 것이 아니다.
DB 스키마 변경, 기존 공고 삭제, 인증키 예산 증액은 없다.

## Rolling 2-Year

공고게시일 기준 최근 2년 유지가 적절하다. 백필과 신규/변경 수집은 별도 진행 지점을 유지하고
장애 시 남은 구간부터 재개해야 한다. 초기 백필 완료가 모든 신규 데이터의 최신성을 뜻하지 않는다.
정리는 posted_at < cutoff만 대상으로 해야 하며 경계와 같은 시각은 보존한다.
현재 prune_central_bids는 기본 읽기 전용, --execute에서만 삭제하며 자동 타이머는 없다.
기존 데이터 보존이 우선인 이번 수정에서는 정리를 자동 활성화하지 않는다.
관심공고의 최소 업무 참조 보존·백업/복구를 확인한 후 일일 정리 작업을 별도 배포하는 것이 적절하다.
외부 API 장애나 일일 한도 때문에 항상 완전한 최신 데이터라는 보장은 할 수 없으므로
마지막 성공·남은 범위·미완료 상태를 정확히 표시해야 한다.
