# 중앙 수집 수명주기와 운영 전환

## 원본 보존과 모델 선택

공고는 기존 Notice의 공식 공고번호·정규화 차수 유일키로 관리하고 rules M2M만 추가한다.
조건 의미를 변경하려면 새 조건을 만든다. 기존 조건/공고/업무 참조는 삭제하지 않는다.
현재 progress 하나로는 백필 중 증분수집을 실행할 때 중단 지점과 완료 증거를 독립 보관할 수 없다.
0003 migration은 기존 CollectionJob에 두 개의 진행 JSON, 대상 시작일, 세대 ID,
로컬 매칭 진행, 마지막 증분 성공을 추가하고 중앙 CollectionWindow 검증 원장을 만든다.
기존 커서·원본·조건은 유지한다. backfill_start가 없는 기존 작업은 backfill_end의 2년 전을 사용한다.
기존 미완료 progress는 해당 모드의 첫 실행에서 가져온다. 이전 수량 근거가 없는 공고 처리 체크포인트는
원본을 삭제하지 않고 다시 대조하며 저장된 원본이 같으면 상세 API를 재호출하지 않는다.

## 상태와 처리

생성은 즉시 BACKFILL_PENDING을 만들며 대상은 생성 시점 기준 최근 2년이다.
worker는 중앙 DB를 UUID 순서로 500건씩 먼저 매칭하고 마지막 위치를 저장한다.
기존 원본의 조건 연결만 추가하며, 중앙 DB에 있다는 이유만으로 그 기간의 완전성을 가정하지 않는다.
API 목록으로 누락을 확인하되 동일 원본의 상세정보는 재사용한다.

BACKFILL_PENDING → BACKFILL_RUNNING → BACKFILL_COMPLETE → INCREMENTAL.
호출 예산/비활성 중단은 PAUSED, 다른 백필 오류는 BACKFILL_FAILED.
백필과 증분 페이지 캐시는 독립 저장되어 다른 모드가 성공해도 미완료 캐시를 덮어쓰지 않는다.
화면에는 백필 상태, 현재 구간 페이지/수신, 기간별 검증 합계, DB 조건 연결 수와 증분 시각을 구분한다.
INCREMENTAL은 처리 모드이며 최신성 보장이 아니다. 별도 증분 커서와 마지막 성공시각을 확인한다.

재활성화는 사용자가 실제 활성화했을 때만 새로운 세대와 현재 기준 최근 2년 검증 대상을 만든다.
기존 원본과 이전 세대 검증 원장은 남긴다. 이미 활성인 조건의 동기화 버튼은 세대를 재생성하지 않는다.
실행 중 재활성화로 세대가 바뀌면 이전 worker는 새 세대 체크포인트를 덮어쓸 수 없다.

## 완료 증거와 수량

공식 응답 totalCount와 목록 수신 수를 대조한다. 페이지 불일치/반복/수량변동은 실패다.
수신 행 = 고유 공고 + 동일 조회 내 중복 행.
처리 고유 공고 = 신규 저장 + 수정 + 기존 동일 원본 + 조건 불일치 + 보관기간 초과.
저장 대상은 실제 Notice/rules 관계가 존재하는지 확인한 뒤 구간 원장과 커서를 같은 트랜잭션에서 확정한다.
각 공고의 UPSERT와 처리 결과 체크포인트 역시 하나의 트랜잭션이다.
조건 전체 완료는 현재 2년 보관 범위부터 backfill_end까지 검증된 구간에 빈틈이 없을 때만 인정한다.
기존 커서는 끝에 도달해도 과거 검증 원장이 없으면 완료로 승계하지 않는다.
먼저 남은 구간을 진행하고 그 뒤 검증 기록이 없는 앞 구간의 목록을 대조한다.

구간 합계에는 경계 분 중복이 있으므로 2년 고유 공고 총수라고 표시하지 않는다.
공식 totalCount는 해당 조회 조건/기간/응답 시점 값이지 불변인 2년 전체 snapshot이 아니다.
최종 조건별 고유 건수는 Notice.rules 관계로 집계한다. 다른 조건과 겹치는 공고는 원본 한 건이다.
기존 275/207건은 9/13 17:26의 관측치이며 새로운 운영 수치를 대신하지 않는다.

## 예산과 신규 공고

G2B_CENTRAL_DAILY_BUDGET 기본 500회는 유지한다. 제공자 승인 한도 10,000은 아직 미확인이다.
G2B_JOB_REQUEST_BUDGET 기본 100회, G2B_JOB_MAX_STEPS 기본 10은 Django 설정/env에서 조정한다.
systemd는 고정 숫자 옵션을 넘기지 않아 런타임 설정을 따른다.
한 실행은 우선 절반의 요청 예산으로 증분 작업을 처리하고, 사용하지 않은 부분을 포함한 나머지로 백필한다.
G2B_INCREMENTAL_REQUEST_RESERVE 기본 100회는 하루 후반 신규 공고를 위해 백필이 사용하지 않는다.
실제 일일 예산보다 큰 예약이나 음수 예약은 실행 시 제한한다. 제공자 quota/auth 오류는 계속 중단한다.
API 요청/응답 행/실제 신규 INSERT/내용 변경 UPDATE를 일자별로 따로 집계한다.
수신 행은 목록 및 상세 API의 합계이며 공고 고유 건수와 다르다.

## 보관과 Tenant 전환

중앙 검색은 기존 posted_at >= retention_start(now) 조건으로 최근 2년만 조회한다.
물리 원본 정리는 관심·투찰·낙찰·계약·실적 참조 보존을 검증할 때까지 보류한다.
기존 prune 명령의 무조건 물리 삭제 실행을 막고 기본 만료 건수 진단만 허용한다.
자동 삭제 타이머는 추가하지 않는다. 향후 일일 정리 작업은 참조가 확인되지 않은 원본을 보수적으로 보존해야 한다.
Tenant 중앙 조회 전환은 기존 review 이행 및 백필 검증 이후 allowlist로 진행한다.
이번 배포는 해당 allowlist를 강제로 켜지 않는다. 미완료 상태에서 데이터가 충분하다고 보고하지 않는다.

## 배포와 rollback

기존 production Environment 승인 아래 중앙 procurement 0003만 추가 적용한다.
진단 명령이 새 필드를 사용하므로 보고는 migration 이후 worker 시작 전에 실행한다.
비활성 초기 조건은 seed 명령이 활성화하지 않는다. 서비스/타이머 설정 rollback은 기존 보호 절차를 유지한다.
코드 rollback 시 추가 필드/원장 데이터는 삭제하지 않는다. 0003 역migration으로 기록을 제거하지 않는다.
운영 완료 보고는 실제 원장의 누락 구간이 없고 증분 커서가 확인된 뒤 수행한다.
