# 중앙 입찰 수집 전환

## 목적과 적용 범위

중앙 관리자가 등록한 업종 또는 공고명 키워드에 해당하는 용역 공고를 중앙에서 한 번 저장한다.
공고게시일 기준 최근 2년을 보관하고 첨부파일은 수집하지 않는다. 공식 나라장터 원문 URL로 이동한다.
이번 변경은 중앙 수집 기반과 기존 회사 목록 연결이다. 실제 보유면허 모델, 복합 자격의 확정 판정,
세부 필터 공통화, 개찰·낙찰 추적은 아직 구현하지 않았다. 모든 후보에 판정 필요를 표시한다.

## 기존 구조를 확장해야 하는 이유

기존 bid.notices/revisions/matches/reviews/sync_runs는 모두 Tenant DB에 있고 동기화 함수가 중앙 alias를 거부한다.
그 테이블을 중앙으로 라우팅하면 기존 검토 FK와 회사별 설정을 손상시키므로 신규 procurement 앱을 중앙에 둔다.
Tenant에는 bid.central_reviews만 추가한다. 중앙 UUID는 공식 공고번호와 정규화한 차수로 결정하며 DB 간 FK는 만들지 않는다.
기존 bid 테이블과 회사 설정은 유지한다. 새 수집조건은 GeoFlow 중앙 관리 화면에서 중앙 관리자만 등록한다.
테넌트 설정은 중앙 수집 범위를 자동 확장하지 않는다.

## 작업 및 누락 처리

중앙 조건마다 독립적인 과거 수집 cursor와 신규/변경 cursor를 둔다. 조건은 OR로 합치고 공고를 중복 저장하지 않는다.
조건의 종류/값 수정은 금지하며 새 조건으로 추가한다. 비활성 조건의 신규 수집은 멈추고 원본은 보관기간까지 유지한다.
한 단계는 최대 하루 구간이며 신규 조회에는 2시간 중첩을 둔다. 변경일시 조회를 별도로 합친다.
수집 완료 전에는 cursor를 이동하지 않는다. 부분 저장 이후 재실행은 UPSERT로 복구한다.
업종/지역 빈 응답을 제한 없음으로 추정하지 않는다. 보조정보 실패는 해당 구간 실패로 남긴다.
업종 검색은 API 검색을 이용하지만 실제 자격 충족을 확정하지 않는다. 키워드를 별도 등록해 업종 없는 공고를 보완한다.
API 검색 자체의 누락 여부는 현장 검증이 필요하며 완전 수집을 보장한다고 표시하지 않는다.
일일 예산은 중앙 작업에 할당한 별도 예산이다. 같은 키를 사용하는 기존 Tenant/외부 스크립트 호출은 합산하지 못하므로 여유를 둔다.
기본 일일 예산은 500회이며 실제 승인 한도 및 다른 사용량을 확인한 뒤 변경한다.

## 배포와 검증 순서

1. 정상 API 응답을 확보한다. 현재 외부 호출 HTTP400/코드10은 해결되지 않았다.
   PPSSrch 조회구분1의 공고게시일, 일반 용역 조회구분3의 변경일시,
   보조정보 조회구분2의 공고번호/차수 조회를 실제 응답으로 검증한다.
   잘못된 응답을 빈 목록으로 해석하거나 cursor를 강제로 넘기지 않는다.
2. 격리 PostgreSQL에서 중앙 migration 및 Tenant 0037 SQL을 적용하고 검토 격리 테스트를 실행한다.
3. 배포 시 중앙 procurement migration을 중앙 DB에만, 0037은 승인된 Tenant DB에만 적용한다.
   기존 라우터의 명시적 Tenant migration 절차를 그대로 사용한다.
4. 중앙 관리자에 필요한 업종 및 GIS 키워드를 등록하고 제한된 과거 구간을 수집한다.
   시스템은 초기 업종을 자동 seed하지 않으며 실제 코드와 범위는 관리자가 명시한다.
5. migrate_central_bid_reviews --database <alias>로 읽기 전용 점검 후 정확한 승인 범위에서 --execute를 사용한다.
   기존 검토 행과 신규 참조의 수/상태/메모를 비교한다. 차수 정규화 충돌은 자동 병합하지 않는다.
6. 정상 표본과 기존 관심공고가 중앙에 확보됐는지 확인 후 G2B_CENTRAL_TENANT_ALIASES에 해당 alias만 추가한다.
   연결 미등록/중앙 context는 거부한다. 기능 플래그 기본값은 빈 목록이다.
7. 운영 경로/계정/환경파일에 맞춰 systemd 예제를 검토하고 승인 후 설치한다.
   timer는 5분마다 큐를 처리하지만 신규/변경 정기 수집은 조건별 1시간 간격이다.
8. 1만~5만 대표 공고로 DB 크기, 검색 실행계획, 동시 수집 중 응답시간을 측정한다.
   현재 검색은 후보 검색이며 title 검색 인덱스 및 코드 관계 정규화의 추가 검증이 필요하다.

## 보존과 복귀

prune_central_bids는 기본 읽기 전용이다. --execute만 2년 초과 중앙 원본/이력을 작은 묶음으로 정리한다.
이 작업은 자동 활성화하지 않는다. Tenant 검토와 공고번호/제목/원문 링크는 삭제하거나 cascade하지 않는다.
보관기간 만료 업무기록의 별도 UI는 후속 작업이므로 정리 작업 활성화 전 해당 화면도 검증해야 한다.
문제가 생기면 collector timer를 중지하고 중앙 읽기 플래그를 제거한다.
전환 후 새로 기록한 central_reviews는 그대로 보존되지만 기존 화면으로 자동 역복사하지 않는다.
복귀 시 이 새 업무기록을 비교/병합할 별도 절차가 필요하다. 단순 플래그 복귀가 무손실 rollback이라고 가정하지 않는다.
운영 schema/data 변경, timer 설치, 배포/재시작, 실제 만료 삭제는 각각 구체적인 운영 승인 후 실행한다.

## 검증 한계

로컬 SQLite 격리 테스트는 수집 지점/중복/실패/예산의 기능 검증이다. PostgreSQL 실행계획이나 운영 속도 증거가 아니다.
PR #310 최초 업로드 CI에서 PostgreSQL 16의 격리 테스트 14건 및 migration 차이 검사가 통과했다.
실제 API 오류가 해결되고 PostgreSQL 검증 및 Tenant 데이터 매핑 검증이 끝나기 전 운영 전환하지 않는다.

## 중앙 관리 화면

운영 중앙 메뉴의 '입찰 수집 관리'(`/control/central/bids/`)에서 업종/키워드를 등록하고
조건별 활성화·비활성화 및 개별/전체 동기화를 요청한다. 기존 `require_central_admin`의
중앙 users.is_staff 검증을 그대로 사용하며 변경 요청에는 CSRF를 적용한다.
기본 Django admin 활성화는 필요하지 않다. 화면과 상태 갱신은 중앙 DB만 조회한다.

총 저장 건수는 공고번호·차수 중복을 제거한 Notice 수이며 2년 초과 정리 대기 건수를 별도로 표시한다.
조건별 건수는 중복될 수 있다. 현재/최근 구간별 전체 확인대상, 처리 건수, 저장·갱신 처리 건수를
분리하며 과거 수집 cursor와 최근 성공 시각도 표시한다. 전체 2년 대상의 미리 확정된 분모는
없으므로 전체 완료율을 추정해서 표시하지 않는다. 상태는 화면에서 10초 간격으로 갱신한다.
비활성화는 다음 작업부터 적용되며 이미 실행 중인 구간은 완료될 수 있다.

추가 중앙 migration `0002_collectionjob_progress`는 기존 CollectionJob에 JSON 진행정보만 추가한다.
기존 fetched_count는 성공한 구간의 최종 조회 건수이므로 실행 중 처리 수량과 실패 직전 수량을
표현할 수 없어 별도 progress가 필요하다. 공고 데이터 및 Tenant 구조는 변경하지 않는다.
실패 시 진행정보와 원래 cursor를 유지하며 재시도 시 구간 진행 건수만 새로 시작한다.
0002 역이전은 진행 표시 정보만 제거하지만, 새 코드가 이를 참조하므로 이전 코드로 복귀 후 수행해야 한다.
운영 migration/배포 및 수집기 활성화는 별도 운영 승인 범위에서 시행한다.
백그라운드 수집기를 설치·실행하기 전에는 동기화 요청만 대기하며 화면이 API를 대신 호출하지 않는다.

## API 건수 진단 사용법

### 보호된 GitHub 진단

`Central bids live diagnostic`은 자동 실행하지 않는 workflow_dispatch 전용이다.
검토된 release/stabilized-deploy에서만 실행하며 기존 production Environment 승인을 그대로 적용한다.
API 인증키만 해당 단계의 환경변수로 전달한다. SSH, 운영 DB 접속, 서버 설정 변경, 재시작은 없다.
scripts/probe_central_g2b.py는 운영 설정 로딩을 거부하고 메모리 SQLite에서만 수집 예산 테이블 등을 생성한다.
이 임시 DB는 프로세스 종료 시 사라지며 실제 중앙/테넌트 migration을 실행하지 않는다.

어제 한국시각 하루의 일반 게시일·검색 게시일·변경일시 조회와 최근 7일의 업종5031 검색을 수행한다.
참가가능지역 API를 최근 7일 등록일시 범위로 조회하고 첫 999행에서 업무구분명에 용역이 포함되며
공고번호·차수·공식 참가가능지역명이 존재하는 표본을 고른다. 용역 목록 API를 공고번호로 다시 조회해
같은 공고번호·차수의 용역 공고인지 검증한 뒤 지역 상세를 공고번호로 재조회한다.
업종 표본의 지역·면허와 별도 지역 표본의 연결키·참가가능지역명을 검증하며 최대 9회 호출한다.
면허·지역 표본·지역 공고번호 재조회·용역 공고번호 재조회는 numOfRows=999, 나머지는 1이다.
지역제한 표본에 연결된 지역명이 없으면 전체 진단 및 배포를 중단한다. 첫 999행에 표본이 없을
경우 NO_RESTRICTED_REGION_SAMPLE로 중단하며, 지역제한 공고가 전국에 없다고 해석하지 않는다.
상세 결과가 표본의 공고번호·차수와 같은지 확인하고 면허 0건은 DETAILS_REQUIRE_REVIEW로 실패 처리한다.
업종 표본의 지역 0건은 제한 없음의 증거가 아니며 계속 확인 필요로 남긴다.
인증/호출한도 오류에는 조기 중단한다. 키워드 및 모든 업종별 의미 검증을 대체하지는 않는다.
출력은 점검 이름·성공여부·건수·오류코드만 포함하고 인증키, URL, 공고 원문, 첨부파일을 남기지 않는다.
이 9회는 같은 인증키의 실제 호출 한도에서 소비되지만 임시 예산은 운영 ApiBudget에 합산되지 않는다.
최근 7일 업종 표본이 없으면 상세검증 미완료(NO_INDUSTRY_SAMPLE)로 표시하며 성공으로 간주하지 않는다.

2026-09-11 배포 #18(run 34614340763)은 지역 표본 선택 실패로 SSH 전에 중단되었다.
공식 공공데이터포털의 내장 Swagger(https://www.data.go.kr/data/15129394/openapi.do)를 확인한 결과
용역 목록에 rgnLmtYn/prtcptLmtYn 필드는 없다. bidPrtcptLmtYn은 일반 입찰참가제한 여부이므로
지역제한으로 대체 해석하지 않는다. 참가가능지역 API의 bsnsDivNm, bidNtceNo, bidNtceOrd,
prtcptPsblRgnNm과 등록일시 범위 조회를 사용하도록 표본 선택을 수정했다.
이 수정은 배포 전 검증에 한정하며 운영 수집기의 전국 판정이나 테넌트 필터를 변경하지 않는다.

2026-09-11 첫 실 진단(run 34611543844)은 기본/검색 조회 모두 2026-09-10 전국 용역 514건,
당일 업종5031 검색 1건, 변경일시 조회 5건으로 성공했다. 전국 첫 표본의 보조정보는 모두 0건이어서
참가자격 상세 연결의 검증 증거로 사용하지 않는다. 이 보완 진단의 실제 실행 결과는 아직 확인 전이다.

2026-09-11 두 번째 진단(run 34612550784)에서는 9월4~10일 업종5031 검색 12건,
선택한 표본의 면허 상세8건과 공고번호·차수 일치를 확인했다. 지역정보는 이 표본에서0건이었다.
이번 지역제한 전용 표본 검증은 배포 작업의 서버 접속 전 단계에서 실행한다.

### 중앙 수집 1차 운영 반영

사용자의 배포 진행 지시에 따라 기존 Production release deploy v2를 다음 순서로 보완했다.

1. production Environment 승인 후 임시 DB의 실 API 진단을 실행한다. 실패하면 서버 접속 전 중단한다.
2. 실행 커밋이 현재 release HEAD인지 다시 확인하고 기존 서비스/환경 rollback 절차를 유지한다.
3. 운영 중앙 default DB에 procurement 0001/0002를 적용하고 초기조건 JSON의 없는 행만 추가한다.
   기존 조건의 이름·활성 상태는 덮어쓰지 않는다. 초기조건은 지하시설물측량업5031, 공공측량업5023,
   수치지도제작업5029, 소프트웨어사업자1468, GIS다. 화면에서 이후 관리한다.
4. 기존 배포의 Tenant 0030~0036 절차는 유지한다. 이번 단계에서0037 적용·검토기록 이전·
   G2B_CENTRAL_TENANT_ALIASES 설정을 하지 않는다. 적재가 끝나기 전에 회사 목록을 전환하지 않는다.
5. 중앙 화면 및 서비스 상태 확인 후 실제 앱 서비스의 실행계정·그룹·경로로 수집기 유닛을 만든다.
   timer는5분마다 작업을 깨우며 조건별 증분 간격1시간, 실행당100회·중앙 일일 기본500회 예산을 유지한다.
6. 실패 시 이전 코드·환경·수집기 유닛과 활성 상태를 복구한다. 중앙 추가형 migration/초기조건은
   삭제하지 않으며 전환 플래그는 그대로다. DB 변경을 무손실 자동 rollback한다고 주장하지 않는다.

운영 승인 대상은 새 release HEAD의 배포 실행 하나다. 과거5faa6d81 배포 승인 대기는 실행하지 않는다.
배포 결과 로그의 central_bids_schema_ok, central_bids_collector_timer_active 및 deployed_sha를 확인한다.
2년 수집은 배포 시 동기적으로 완료하지 않고 백그라운드로 이어간다. 적재완료·회사 검토기록 대조 후

현재 GitHub 연결은 workflow_dispatch 최초 실행 도구를 제공하지 않아 사용자 실행이 필요하다.
이 워크플로 실행을 배포, 운영 migration, 수집 timer 활성화의 승인으로 해석하지 않는다.

### 기존 진단 명령

`inspect_g2b_bids --start 202609100000 --end 202609102359 --industry 5031`

겹칠 수 있으므로 조건별 합계를 전체 고유 건수라고 표시하지 않는다. 조건 통합 고유 건수는 수집 후
공고번호·차수 기준 DB에서 계산한다. 이 진단은 용역만 대상으로 하며 공사/물품 집계는 별도 오퍼레이션이 필요하다.
현재 실행 환경의 외부 요청 승인 취소로 이 추가 명령의 실 API 검증은 수행하지 못했다.

## 맞춤공고 · 개인 저장/숨김 (현재 변경)

기존 회사 검토 상태/메모는 상세 영역에서 그대로 유지한다. 목록의 별표와 숨김은
회사 공통 검토와 별개이며 `bid.personal_state`가 tenant DB에서 중앙 사용자 UUID,
origin(central/legacy), 공고 UUID별로 소유한다. 중앙 원본 및 다른 사용자/회사의 상태는
수정하지 않는다. CSRF가 적용된 POST와 기존 `contracts.view`/tenant 검증을 통과한
사용자만 자신의 상태를 변경한다. actor는 요청값이 아니라 기존 중앙 사용자 조회로 확정한다.
최대 30건을 원자적으로 저장/숨김/복원하며 두 플래그는 독립적으로 보존한다.

맞춤공고는 투찰마감 경과·취소를 기본 제외하고 마감 미확인 공고는 유지한다.
마감 포함, 공고일 범위, 정렬, 기존 회사 검토 필터로 조회한다. 숨김 조건은 건수/페이지
계산 전에 적용한다. 저장한 공고와 숨긴 공고는 회사의 선택 조건이 변경되어도 조회하며
마감 후에도 유지한다. 다만 기존 중앙 원본 2년 보관범위 안에서 조회한다. 원본 정리 시
개인 상태를 삭제하지 않지만 만료 원본의 별도 보관 화면은 아직 없다.
기존 회사 관심/참여검토는 개인 별표로 자동 변환하지 않으며 상세 기록으로 보존한다.

설정은 검색 가능한 체크박스 선택창으로 기존 조건의 활성 상태를 관리한다.
등록된 업종은 중앙 기준에서 선택한다. 지역/기관은 기존 등록 항목을 선택하고 추가
등록 폼을 접어 제공한다. 전국 시군구 표준 사전·계층 선택은 아직 제공하지 않는다.
수집 키워드 직접 추가는 이번에 승인된 정책 변경이다. manager 권한을 가진 tenant
설정 담당자가 명시적으로 추가하면 기존 중앙 키워드를 대소문자 구분 없이 재사용하고,
새 키워드는 중앙 작업을 만들고 해당 회사에 선택한다. 중지한 조건은 자동 활성화하지 않는다.
중앙과 tenant 사이에는 분산 트랜잭션이 없으므로 연결 실패 후 재시도 시 같은 조건을
재사용한다. 생성된 중앙 조건은 관리 화면에서 확인할 수 있다.
기존 결과 내 포함/제외 키워드는 수집조건과 구분하며 이전 설정을 임의 해제하지 않는다.

한전은 아래 출처별 중앙 수집 구조로 연결한다. LH는 '연동 준비 중'으로 선택할 수 없다.
인증키 자체를 코드·DB·로그에 넣지 않는다. 이번 변경은 해당 수집기를 구현하지 않는다.

## 한전 중앙 수집과 명시적인 검색 범위

중앙 `CollectionRule.source`와 `Notice.source`는 `g2b`/`kepco`를 구분한다.
수집조건의 고유키는 출처·종류·값, 공고 고유키는 출처·공고번호·차수이다.
기존 나라장터 UUID는 바꾸지 않으며 한전 UUID는 별도 namespace 문자열로 생성한다.
한전 응답에는 차수가 없어 `0`을 사용하고 같은 번호의 변경은 NoticeRevision에 보관한다.
중앙 migration 0005는 기존 행을 g2b로 유지한다. 한전 적재 후 이전 고유키로 역이전하면
기관 간 동일 번호 충돌 가능성이 있으므로 데이터 보존 후 roll-forward 수정한다.
이 migration 적용 후 배포가 실패하여 출처 미지원 코드로 복귀할 때는 수집 timer를 중지 상태로 유지한다.
이전 수집기가 한전 조건을 나라장터에 요청하지 않게 하고 후속 roll-forward 배포로 복구한다.

`procurement.kepco.KepcoClient`는 전력 데이터개방포털 공식 전자입찰 계약정보
`https://bigdata.kepco.co.kr/openapi/v1/electContract.do`를 POST로 호출한다.
공식 가이드: `https://bigdata.kepco.co.kr/cmsmain.do?scode=S01&pcode=000493&pstate=contract`.
회사 COM01, 용역 Service만 보관한다. 한전은 업종코드 검색을 제공하지 않으므로
업종 조건은 참가자격(bidAttendRestrict/etc)의 업종명 일치 후보이며, 키워드는 제목 일치이다.
두 종류는 독립 수집조건으로 등록한다. 등록 업종·키워드에 맞는 공고만 중앙에 보관하며
여러 조건에서 발견한 공고는 1건에 조건 연결만 추가한다. 미확인 지역을 전국으로 추정하지 않는다.
나라장터 코드와 한전 업종명을 자동으로 동등 자격으로 판정하지 않는다.

날짜별 응답을 완전히 읽고 JSON·식별자·날짜를 검증한다. HTTP 404는 공식 무자료 응답,
그 외 오류·응답 상한 초과·형식 오류는 실패로 남기며 진행 기간을 완료 처리하지 않는다.
날짜별로 조건에 맞는 후보만 중단 지점에 저장해 요청예산 소진 후 이어간다.
요청 횟수는 기존 중앙 공통 예산에 포함한다. provider_received는 필터 전 응답 행 수,
처리·저장 건수는 필터 후 후보 수이며 서로 같은 수라고 표시하지 않는다.
첨부파일은 안전한 한전 호스트의 링크만 보관하고 다운로드하지 않는다.

기존 수집 timer/worker가 두 출처를 처리한다. `collect_central_bids --source kepco`로
출처별 한정 실행도 가능하다. 신규 한전 조건은 기존 기간 설정에 따라 과거 수집을 시작한다.
증분은 변경일 API가 없는 한전 특성 때문에 최근 30일 공고를 다시 조회한다.
30일보다 오래된 공고의 정정은 과거 재수집이 필요하다. 모든 과거 정정을 실시간 수집한다고 보장하지 않는다.

테넌트는 중앙 공고만 조회하고 개인 관심·숨김 및 회사 검토기록은 기존 tenant DB에 유지한다.
테넌트 설정은 기관과 독립적인 논리 업종/키워드를 선택한다. 중앙 관리 화면도 논리 조건으로 묶어
표시하고 펼친 내부 규칙에서 출처별 등록·수집 상태·저장 수량을 관리한다.
새 기관의 규칙을 기존 논리 조건에 연결하면 기존 선택에 자동 적용되며 테넌트 선택을 추가하지 않는다.

목록의 `맞춤공고`는 선택한 업종 OR 수집키워드와 설정 지역을 적용한다.
`중앙 저장공고 검색`은 선택 조건·설정 지역을 생략하고 중앙의 최근 2년 저장 공고를 검색한다.
어느 범위에서도 개인 숨김은 유지하고, 마감·취소 및 회사 '참여 안 함'은 명시적인 포함 옵션으로 조회한다.
추가 기관·포함·제외 키워드는 기본 미적용이며 목록에서 '추가 적용'을 켠 경우에만 반영한다.
기존 설정값은 삭제하지 않는다. 회사 '관심'은 개인 별표로 복사하지 않고 별도 조회 링크로 제공한다.
중앙 저장 검색은 공개 공고의 범위를 넓힐 뿐 타 테넌트 개인/검토 데이터에 접근하지 않는다.

운영 연결은 GitHub production Environment의 `KEPCO_API_KEY`가 필요하다.
배포는 G2B/한전 비밀값을 보호된 임시 파일로 전송하고 서버 .env를 원자적으로 교체한다.
임시 파일은 정리하며 키 자체는 코드·진행정보·오류문에 기록하지 않는다.
서버 비밀값은 지속 수집에 필요하므로 폐기하지 않으며 교체는 별도 운영 작업이다.
보호된 production 승인 경계를 유지하고, 공식 API live probe가 성공해야 배포 점검을 통과한다.
검증과 운영 반영 결과는 PR 및 배포 실행 결과를 기준으로 판단한다.


## 논리 관심조건과 기관별 규칙 분리

### 목적·현재 구현

기존 `bid.central_preferences.rule_ids`는 중앙 `CollectionRule` UUID를 직접 저장했다.
나라장터 업종을 선택한 뒤 같은 업종의 한전 규칙이 등록되어도 UUID가 달라 후보가 누락될 수 있었다.
표시 이름은 식별자가 아니다. 명시적인 조건 키로 연결하며 기관명을 문자열에서 제거해 묶지 않는다.

중앙의 `InterestCondition(kind,key,name,active)`가 사용자 관심조건의 원본이다.
기존 `CollectionRule`에 `condition` FK를 추가하여 하나의 논리 업종에 N개 기관별 matcher를 연결한다.
기관별 `(source,kind,value)`, `CollectionJob` 및 `Notice.rules`는 그대로 재사용한다.
현재 업종은 다음과 같이 연결하며 기존 기타 업종은 독립 조건으로 보존한다. 측지측량업은 추가하지 않는다.

| 논리 키 | 사용자 업종 | G2B 값 | KEPCO 값 |
| --- | --- | --- | --- |
| public-survey | 공공측량업 | 5023 | 공공측량업 |
| underground-survey | 지하시설물측량업 | 5031 | 지하시설물측량업 |
| digital-map | 수치지도제작업 | 5029 | 수치지도제작업 |
| software-business | 소프트웨어사업자 | 1468 | 기존 규칙 없음 |

기존 키워드는 기존 matcher의 공백 제거·casefold 정책으로 통합한다. 한글 부분 포함 검색과
ASCII 토큰 경계 정책은 바꾸지 않는다. `지하시설물`은 `지하 시설물도`에도 매칭된다.

Tenant에는 새 테이블이나 DB 간 FK를 만들지 않는다. 기존 JSONB `rule_ids` 컬럼에 논리 UUID를
저장하며 새 설정 POST는 논리 UUID만 받는다. 읽기 resolver는 기존 기관별 UUID도 받아 논리 조건을
거쳐 현재 연결된 모든 기관별 규칙으로 확장한다. 따라서 명시적 tenant 변환 전에도 기존 선택 의미가
유지된다. 조건 없는 기존 행은 호환 조회만 지원하고 변환 명령은 해당 행을 발견하면 중단한다.
없는 설정 행의 기존 G2B 업종 fallback과 명시적인 빈 선택의 차이를 유지한다.

논리 `active=False`는 신규 선택을 막는다. 이미 선택된 조건·과거 공고 관계는 보존한다.
기관별 `CollectionRule.active`는 실제 수집 중지를 관리하며 논리 활성 상태와 혼동하지 않는다.
자동 변환은 기존 규칙의 이름·활성 상태, 작업 cursor, 원본, 검토·개인 상태를 변경하지 않는다.
테넌트 키워드 추가는 하나의 논리 조건 아래 설정된 `PROCUREMENT_KEYWORD_SOURCES`의 규칙을
등록한다(기본값: 등록된 source 목록). 기존 중지 규칙을 재활성화하지 않는다.

새 기관의 adapter를 구현한 뒤 기존 논리 조건을 선택해 source rule을 등록하면 resolver가 자동 확장한다.
기관별 업종 코드/표현은 명시적 mapping으로 관리한다. seed 파일의 `condition_key` 또는 중앙 관리
폼의 논리 조건 연결을 사용한다. 미확정 업종은 별도 legacy 조건으로 보존하고 운영 담당자가 검토한다.
기존 source rule의 identity와 연결은 수정 화면에서 잠그고, matcher 의미를 바꿀 때 기존 provenance를 보존한다.

### 중앙·테넌트 책임과 코드 위치

중앙은 API 수집, 정규화, source별 공고 식별·UPSERT, 2년 rolling cache, matcher 실행과
논리 조건 mapping을 소유한다. 테넌트는 관심조건 선택 및 중앙 원본 조회, 지역 필터와 검토·개인 상태를
소유한다. 관심조건은 OR이고 지역 등 기존 후속 필터는 유지한다. 여러 rule이 같은 공고에 매칭되어도
`(source,number,order)` 원본은 하나이며 목록은 distinct 조회한다. 테넌트별 API 재수집은 없다.

권한은 기존 중앙 관리자 검증, 테넌트 manager 설정 검증 및 CSRF를 그대로 사용한다.
입찰 이외 업무 및 사용자/권한 구조는 변경하지 않는다. 결과 목록·상세의 공고 출처 표시는 유지한다.

- 모델·resolver: `procurement/models.py`, `procurement/conditions.py`
- 테넌트 선택·목록: `procurement/preferences.py`, `procurement/tenant.py`, `geoflow_ops/bids/views.py`
- 중앙 수집·matcher: `procurement/service.py`, `procurement/kepco.py`, `geoflow_ops/bids/matcher.py`
- 중앙 관리: `procurement/views_central.py`, `procurement/dashboard.py`, `procurement/admin.py`
- seed mapping: `deploy/bids/initial-rules.json`, `deploy/bids/kepco-rules.json`

### Migration과 승인 후 적용 절차

이 변경은 구현 및 격리 검증 대상이다. 운영 migration·배포·timer 재시작은 별도 승인 전 실행하지 않는다.
기존 배포 workflow는 중앙 procurement migration을 최신까지 적용하므로 이 PR을 병합한 뒤에도
운영 workflow를 승인 없이 실행하지 않는다. 테넌트 선택 변환은 자동 배포에 넣지 않는다.

1. 중앙/대상 테넌트 DB와 현재 코드를 백업하고, 대상 alias 및 기존 선택을 확인한다.
2. 승인된 점검 시간에 수집 worker와 앱의 schema 변경 동시 접근을 멈춘다.
3. 중앙 DB에만 `python manage.py migrate procurement --database=default --noinput`을 적용한다.
   0006은 논리 조건과 FK를 추가하고, 0007은 명시적 매핑으로 기존 규칙을 연결한다.
   위 default는 실제 `CENTRAL_DB_ALIAS`가 default인 배포 기준이다. 다른 구성은 해당 alias를 사용한다.
4. 새 앱 코드로 중앙/테넌트 읽기를 확인한다. 기존 tenant `rule_ids`도 resolver가 지원한다.
5. 각 활성 tenant에 아래 dry-run을 실행한 뒤 승인 범위 안에서 execute한다.
   `cheonan_db`는 현재 운영 설정 예이며 다른 회사에는 해당 alias를 명시한다.

```bash
python manage.py migrate_bid_interest_conditions --database=cheonan_db
python manage.py migrate_bid_interest_conditions --database=cheonan_db --execute --backup-file=/secure/cheonan-interest-before.json
```

변환은 PostgreSQL 테이블 잠금 및 트랜잭션 안에서 수행한다. 새 mode0600 백업 파일을 먼저
생성·fsync한 후 UPDATE하며 기존 파일을 덮어쓰지 않는다. 알려지지 않은 UUID나 미연결 규칙은
원본을 유지하고 오류로 중단한다. 재실행 시 이미 변환된 값은 변경하지 않는다.
테넌트 schema migration은 추가하지 않는다. 기존 0038 central_preferences가 있어야 한다.

6. 실제 공고/선택/목록을 대조하고 기존 수집·증분·backfill 정상 여부를 확인한 뒤 승인 범위대로 재개한다.
7. 복귀가 필요하면 현재 설정이 백업의 변환 후 값과 같을 때만 아래 guarded restore를 사용한다.
   이후 사용자가 수정한 설정은 자동 덮어쓰지 않는다.

```bash
python manage.py migrate_bid_interest_conditions --database=cheonan_db --restore-file=/secure/cheonan-interest-before.json
python manage.py migrate_bid_interest_conditions --database=cheonan_db --restore-file=/secure/cheonan-interest-before.json --execute --backup-file=/secure/cheonan-interest-restore-before.json
```

새 logical UUID로 저장된 설정을 복구하지 않고 구버전 코드로 돌아가면 조회가 누락될 수 있다.
새로 추가·변경한 설정은 별도 대조해야 하므로 단순 코드 rollback을 무손실 복구로 간주하지 않는다.
중앙 0007은 역방향 데이터를 삭제하지 않는다. 운영 0006 역이전으로 조건을 삭제하지 말고
테넌트 백업 보존 및 roll-forward 수정을 우선한다.

### E012607882 검증과 남은 사항

공개 재현 공고의 제목은 `서산지역 전기공급시설 전력구공사(서산-성연) 지하시설물도 작성용역`이다.
공개 재현 본문(https://work.00data.kr/projects/KPE012607882)의 참가자격에 공공측량업(또는 측지측량업),
수치지도제작업, 지하시설물측량업이 함께 기재되어 있다. 이는 후보 matcher 회귀 표본에만 사용하며
실제 KEPCO API 응답을 확보했다는 증거로 사용하지 않는다. 후보 검색의 OR를 입찰 자격의 OR로 해석하지 않는다.

`procurement/test_conditions.py`의 해당 번호 표본은 API 형식에 맞춘 합성 fixture임을 명시한다.
실 API 수신, 운영 중앙 저장·rule 관계, 실제 테넌트 노출은 별도 확인이 필요하다.
이번 작업 세션에서 운영 중앙 화면은 권한 없음으로 조회가 막혔다. DB/API 값은 추측하지 않는다.

승인된 읽기 환경에서 다음 명령으로 실제 중앙 원본·저장 rule·현재 matcher·논리 조건·테넌트 선택 및
후속 지역/검토 필터 결과를 대조할 수 있다. 이 명령은 API 호출이나 DB 변경을 수행하지 않는다.

```bash
python manage.py diagnose_bid_notice_conditions --database=cheonan_db --number=E012607882 --source=kepco
```

실제 API JSON 파일을 별도로 확보한 경우에만 `--api-response=/secure/kepco-response.json`을 추가한다.
파일이 없으면 `api_received`는 null(미확인)이다. 개인 숨김까지 확인하려면 해당 중앙 사용자 UUID를
`--user-id`로 명시한다. 생략하면 회사 후보 목록만 검증하며 실제 사용자별 표시를 확정하지 않는다.
기본 목록과 마감 포함 목록, 개인 숨김·회사 참여 안 함·지역 설정에 의한 제외를 구분한다.
이 명령은 새 중앙 schema가 필요하므로 기존 운영 schema에서 무작정 실행하지 않는다.

검증 범위는 기존 선택 변환·백업·보호 복원, 신규 source 동적 확장, G2B/한전 결과 통합,
공고 중복 방지, 키워드 공백·접미사, 출처 표시와 기존 수집 회귀를 포함한다.
PostgreSQL 전용 검증은 CI의 격리 DB에서 실행한다. 실제 API/운영 공고 검증 및 데이터 규모별
query 실행계획·성능은 운영 반영 전 남은 항목이다.

## 회사별 맞춤검색과 간소화 목록 (2026-11)

### 업무 흐름과 소유권

목록의 정상 업무는 관심 등록·해제, 기록, 개인 숨김·복원으로 구성한다. 기존
미검토/검토 중/참여 검토/참여 안 함 선택 UI는 제공하지 않는다. 과거 검토 상태와 메모는
삭제하지 않으며 목록 메뉴의 이전 회사 관심기록/전환 전 검토기록에서 조회한다.
기존 `excluded` 상태는 정상 웹 목록을 자동으로 숨기지 않는다. 명시적인 개인 숨김만 적용한다.
관심은 기존 `bid.personal_state.saved`, 숨김은 `hidden`을 그대로 사용하며 서로 독립이다.
과거 회사 관심을 임의로 모든 사용자의 개인 관심으로 복제하지 않는다.
메모 저장은 기존 검토 상태를 변경하지 않는다. 메모는 목록 입력창 대신 상세·기록 모달에 둔다.

회사별 검색은 기존 `ops.my_org_units` UUID를 참조하는 tenant `bid.company_search_profiles`에
저장한다. 소유 회사와 개인정보 접근권한 모델을 새로 도입하는 작업이 아니다. 이름으로 회사·지점
관계를 추론하지 않으며 자회사의 설정이나 업종을 모회사에서 자동 상속하지 않는다.
회사 선택은 검색 기준이다. 관심·숨김은 기존 사용자 범위, 메모는 기존 테넌트 공유 범위를 유지하며
화면에 이를 명시한다. 계약·프로젝트·직원·재무의 소유권/접근권한은 이번 변경 대상이 아니다.

검색설정은 회사당 한 벌이며 중앙 논리 관심조건 UUID, tenant 등록 지역/기관/포함·제외 키워드의
UUID 선택, 출처, 명시적으로 확인한 관내 기준지역을 저장한다. 원본 공고나 기업 주소를 복제하지 않는다.
기존 singleton `bid.central_preferences`와 active 필터는 공통 기본조건으로 유지한다.
회사 설정이 없으면 공통 조건을 보여주고 첫 저장 시 선택을 확정한다. 저장한 뒤에는 공통 선택이
변해도 회사의 선택을 덮어쓰지 않는다. 명시적인 빈 업종·수집키워드는 맞춤공고 0건이고, 빈 지역이나
출처는 해당 항목으로 제한하지 않는 뜻이다. 회사 ID와 선택 항목은 tenant에서 서버 검증한다.
조회는 기존 입찰 조회 권한, 설정 변경은 기존 입찰 쓰기+manager 역할을 재사용한다.

회사별로 업종 OR 수집키워드 후보를 선택한 뒤 관심지역을 적용한다. 전국·지역 미확인은 포함한다.
기관·포함·제외 키워드는 목록에서 추가 적용을 켤 때만 사용한다. 전체 공고 검색은 회사의 수집조건·
설정지역·출처 제한을 우회하며 명시적인 상세필터는 적용한다. 관심/숨김 목록은 회사 검색조건과
마감 여부에 독립적으로 유지된다. 기간·검색어·명시적 출처 필터는 적용된다.
중앙 수집·기관별 조건 resolver·중복 제거·보존기간은 유지한다. 회사에서 수집 키워드를 추가하면
중앙의 기존 논리조건/기관별 rule을 재사용하고 필요한 job을 준비하며 그 회사의 설정에만 추가한다.

### 목록과 표시 근거

기본 열은 공고명/출처, 발주기관, 금액 종류를 명시한 금액, 마감, 관리다. 지역·업종 중복 열과
상시 회사 메모 입력창을 제거한다. 관심·상세/기록·숨김 버튼은 같은 관리 셀에 둔다.
투찰 마감과 확인 가능한 나라장터 참가등록 마감(`bidQlfctRgstDt`)을 표시한다.
계약·입찰·낙찰 방식 필드가 있는 경우에만 협상/수의시담/전자시담/직찰/직접입찰 배지를 표시한다.
제목으로 방식을 추정하지 않으며 한전의 미확인 방식 필드를 임의 매핑하지 않는다.

관내는 회사 설정에서 확인한 시·군·구 기준과 공고의 참가제한 지역이 정식명칭/등록 별칭으로
정확히 일치할 때만 표시한다. 도 전체·광역시 전체·복수 지역·정보 없음은 관내로 추정하지 않는다.
등록 주소와 일치하는 후보를 설정 화면에서 제안하지만 자동 선택하지 않는다. 기준지역 선택은
참가자격을 보증하거나 관심지역을 자동 변경하지 않는다. 상세에는 지역·업종·원문 링크를 유지한다.
보유 면허 코드의 자동 연동과 회사별 비공개 관심·메모·서류는 후속 범위다.

사용자는 이번 입찰 개편 및 배포를 요청했다. 기존 보호된 production 배포는 중앙 입찰 연동이
활성화된 검증된 tenant에만 0038 선행을 확인하고 0053 SQL을 적용한다. 기존 선택/관심/검토를
일괄 변경하거나 기업 주소·업종을 추론해 백필하지 않는다. 다른 업무 migration을 새로 실행하지 않는다.
기존 배포의 트랜잭션 dry-run, 적용 확인, 코드·환경 rollback과 production 승인 경계를 유지한다.
코드 rollback 시 추가 테이블·회사 설정은 보존한다. 역 migration으로 업무기록을 삭제하지 않는다.

검증에는 회사/tenant 분리, 다른 tenant 회사 및 미등록 조건 거부, 빈 선택, 업종/키워드 OR,
회사 출처 필터와 전체검색 차이, 관심목록의 조건 독립성, 정확한 관내 표시, 원문 방식 필드,
메모 저장 시 과거 상태 보존, 템플릿 렌더를 포함한다. PostgreSQL migration/저장 검증은 CI의
격리 DB에서 수행한다. 구현·검증과 운영 배포 완료는 구분하며 실제 결과는 PR/배포 로그로 확인한다.
