# GeoFlow Finance Architecture & Decision Record

> 상태: 현재 구현 + 확정된 차기 설계 원칙
>
> 기준일: 2026-09-03
>
> 기준 브랜치: `release/stabilized-deploy`

## 1. 목적

GeoFlow Finance는 계약 업무에서 발생하는 청구, 세금계산서, 지급, 입출금, 계좌/카드, 증빙을 별도의 재무 영역에서 일관되게 관리하기 위한 기능이다.

핵심 목표는 다음과 같다.

- 같은 내용을 계약, 프로젝트, Finance에 반복 입력하지 않는다.
- 계약과 연결된 재무 흐름을 추적할 수 있어야 한다.
- 회사가 여러 개인 경우 귀속회사를 명확히 분리한다.
- Excel/은행자료를 가져올 수 있어야 한다.
- 잘못 입력한 데이터는 복구 가능한 삭제 구조를 사용한다.
- 증빙은 private S3에 저장하고 Finance 레코드와 연결한다.
- 계약/프로젝트 타임라인은 Finance 데이터를 복제하지 않고 통합 조회한다.

---

## 2. 가장 중요한 원칙: Finance가 재무 데이터의 Source of Truth

청구, 세금계산서, 입금/출금 등 재무 사실의 원본은 Finance에만 둔다.

예를 들어 사용자가 Finance에서 청구를 등록했다고 해서 같은 내용을 계약 이벤트 테이블에 다시 `청구 완료` 이벤트로 저장하지 않는다.

그 대신 계약 상세의 타임라인을 표시할 때 다음 두 종류의 데이터를 함께 조회한다.

1. 계약/프로젝트에서 실제로 등록한 업무 이벤트
2. Finance에 존재하는 청구, 세금계산서, 입출금 등 재무 레코드

즉, **데이터는 한 번만 저장하고 화면에서는 여러 도메인의 데이터를 합쳐 보여준다.**

이 원칙은 2026-09-03 논의에서 확정했다. 타임라인 통합 조회 자체는 차기 구현 항목이며, 이 문서는 그 구현 기준을 정의한다.

## 3. 관계 구조

### 3.1 계약

Finance의 기본 연결축은 계약이다.

- 청구, 세금계산서, 지급, 입출금은 가능하면 계약과 연결한다.
- 계약 선택 시 계약의 귀속회사와 발주처 정보를 기본값으로 사용할 수 있다.
- Finance 화면에서 계약을 선택하면 해당 계약의 내부 회사(`org_unit_id`)와 발주처(`client_id`)를 기본값으로 채운다.
- 거래처는 사용자가 필요한 경우 변경할 수 있다.

### 3.2 프로젝트

프로젝트는 Finance의 필수 축이 아니다.

- 계약 1건에 프로젝트가 여러 개일 수 있다.
- 프로젝트가 정확히 1개인 계약은 내부적으로 자동 연결할 수 있다.
- 여러 프로젝트가 있는 계약에서 Finance 사용자가 불필요하게 프로젝트를 선택하도록 강제하지 않는다.
- 향후 프로젝트별 원가/손익 분석이 필요하면 프로젝트 연결을 활용한다.

### 3.3 거래처

거래처는 기존 partner/master 데이터를 참조한다.

- 계약의 발주처를 기본 거래처로 사용할 수 있다.
- 계약 선택 후 사용자가 다른 거래처로 변경 가능하다.
- Excel import 시 사업자번호 또는 이름으로 매칭한다.
- 매칭되지 않은 외부 거래처 정보는 원본 문자열을 보존하는 방향을 사용한다.

### 3.4 귀속회사

여러 법인/회사 단위 재무를 분리하기 위해 `my_org_unit_id`를 Finance의 공통 축으로 사용한다.

적용 대상에는 다음이 포함된다.

- 계좌
- 카드
- 청구
- 지급
- 세금계산서
- 입출금

Finance 상단의 귀속회사 필터는 세션에 유지되며, 목록과 대시보드 집계에 같이 적용한다.

## 4. Finance 기능 영역

현재 Finance는 목록 우선(list-first) UI와 Bootstrap modal 입력/수정 방식을 사용한다.

### 4.1 대시보드

- 청구/지급/입출금 등 Finance 요약
- 귀속회사 필터 반영
- 삭제된 데이터는 집계에서 제외

### 4.2 청구

청구는 계약에 대한 대금 청구 사실을 관리한다.

주요 연결값:

- 계약
- 선택적 프로젝트
- 귀속회사
- 거래처
- 금액
- 상태
- 증빙/첨부

향후 계약 타임라인에서 청구를 별도 이벤트 입력으로 만들지 않고, Finance 청구 레코드를 직접 읽어 표시한다.

### 4.3 세금계산서

세금계산서는 매출/매입 계산서 데이터를 관리한다.

주요 정보:

- 발행/작성일
- 매출/매입 구분
- 거래처
- 계약
- 공급가액
- 부가세
- 합계
- 승인번호 또는 계산서 식별값
- 상태
- 증빙

HomeTax Excel import를 지원한다.

### 4.4 지급

지급 요청/지급 관련 데이터를 Finance에서 관리한다.

계약과 연결할 수 있으나 실제 지급 대상 거래처는 계약 발주처와 다를 수 있으므로 사용자 선택을 허용한다.

### 4.5 입출금대장

은행 거래를 중심으로 다음을 관리한다.

- 거래일자
- 입금/출금
- 금액
- 거래처
- 계좌
- 적요
- 계약
- 분류
- 증빙

은행 XLS/XLSX import를 지원한다.

### 4.6 계좌와 카드

계좌/카드는 귀속회사에 연결한다.

- 계좌와 카드도 soft delete 대상이다.
- 계좌는 거래내역에서 참조 중이면 영구삭제를 차단한다.
- 카드도 동일한 공통 삭제함 UX를 사용한다.

### 4.7 증빙

Finance 증빙은 private S3를 사용한다.

원칙:

- short-lived presigned URL 사용
- 업로드 완료 후 attachment와 Finance 레코드를 연결
- 다운로드도 signed URL을 통해 수행
- 활성 웹/스크립트 유형 업로드 제한
- 업로드 크기 제한

## 5. 설정값 구조

Finance의 상태, 유형, 분류 등 업무 코드값은 화면 문자열에 하드코딩하지 않고 가능한 범위에서 `ops.settings_nodes`를 사용한다.

이 원칙을 사용하는 이유:

- 표시명 변경 시 코드 수정 최소화
- 회사/업무별 설정 확장
- 코드값과 표시명 분리
- 향후 관리자 설정 화면과 연결 가능

Finance 목록에서는 저장된 코드가 그대로 노출되지 않도록 설정값의 표시명을 사용한다.

## 6. Excel Import 원칙

### 6.1 공통 원칙

- Excel 저장 전에 반드시 preview를 거친다.
- header 자동 인식을 지원한다.
- 파일마다 header 행 위치가 다른 경우를 고려한다.
- 중복 가능성을 표시한다.
- 선택된 행만 저장할 수 있다.
- 계약과 거래처는 행별 매핑이 가능해야 한다.

### 6.2 source page가 import 유형을 결정

사용자가 import popup 안에서 다시 유형을 선택하지 않는다.

- 세금계산서 화면에서 열면 세금계산서 import
- 입출금대장 화면에서 열면 거래내역 import

즉, source page가 의미를 결정하고 import popup은 해당 데이터만 처리한다.

### 6.3 행별 계약/거래처 매핑

preview 각 행에서 계약과 거래처를 연결할 수 있다.

- 계약 선택 시 계약 발주처를 기본 거래처로 선택
- 사용자는 거래처를 변경 가능
- 체크된 여러 행에 계약/거래처를 일괄 적용 가능

### 6.4 은행 Excel

IBK와 농협 등 서로 다른 형식을 처리하기 위해 다음을 지원한다.

- `.xlsx`
- legacy `.xls`
- 상위 여러 행에서 header 탐색
- 입금/출금 금액이 별도 컬럼인 형식
- 거래일시/적요/상대은행/예금주 등의 서로 다른 header alias

현재 reader는 `python-calamine`을 사용한다.

## 7. 삭제 정책

Finance 데이터는 실무 이력과 연결되므로 일반 삭제는 hard delete를 사용하지 않는다.

### 7.1 일반 삭제

- `is_deleted = true`
- `deleted_at` 저장
- `deleted_by` 저장

삭제된 데이터는 일반 목록과 집계에서 제외한다.

### 7.2 삭제함

공통 Finance 삭제함에서 다음 유형을 함께 관리한다.

- 청구
- 세금계산서
- 지급
- 입출금
- 계좌
- 카드

삭제함에서는 복원 또는 영구삭제를 수행한다.

### 7.3 영구삭제

- `tenant_admin`만 수행
- 다른 레코드에서 참조되는 경우 영구삭제 차단
- 특히 계좌가 거래내역에서 참조 중이면 삭제 금지

## 9. 계약/프로젝트 타임라인 통합 설계

> 상태: **결정됨 / 미구현**

### 9.1 기존 문제

계약 타임라인에 `청구` 이벤트를 직접 등록하고, 다시 Finance에서 같은 청구를 입력하면 이중 입력이 된다.

같은 데이터가 두 테이블에 존재하면 다음 문제가 생긴다.

- 금액 또는 날짜 불일치
- 한쪽만 수정되는 문제
- 삭제/취소 시 동기화 문제
- 무엇이 원본인지 불명확

### 9.2 확정 방향

청구/세금계산서/입금과 같은 재무 항목은 계약 이벤트 입력 항목에서 제외한다.

Finance에서 실제 데이터를 입력하면 계약 타임라인은 Finance 테이블을 직접 읽어서 표시한다.

계약 타임라인은 하나의 이벤트 테이블을 읽는 화면이 아니라, 여러 source를 시간순으로 합치는 **통합 활동 타임라인**이 된다.

### 9.3 기본 표시 구조

계약 상세의 기본 타임라인에는 다음을 보여준다.

- 계약 차원의 주요 업무 이벤트
- Finance의 주요 재무 활동
  - 청구 등록
  - 세금계산서 발행
  - 입금
  - 필요 시 지급/출금

프로젝트의 세부 업무 이벤트는 기본적으로 숨긴다.

예:

- 현장작업 시작/완료/중지
- 성과심사 제출
- 성과심사 반려/보완
- 프로젝트 내부 작업 상태

### 9.4 모두 보기

계약 상세에 `모두 보기` 옵션을 제공할 수 있다.

기본:

```text
계약 주요 이벤트 + Finance 주요 활동
```

모두 보기:

```text
계약 주요 이벤트
+ Finance 주요 활동
+ 계약에 속한 모든 프로젝트의 상세 이벤트
```

이렇게 하면 계약의 전체 이력을 확인할 수 있으면서도 평소 타임라인이 프로젝트 세부 이벤트로 과밀해지는 것을 방지한다.

### 9.5 데이터 중복 금지

향후 구현 시 다음과 같은 자동복제 방식은 원칙적으로 사용하지 않는다.

```text
Finance 청구 저장
-> contract_event에 '청구 완료' INSERT
```

대신 다음처럼 조회 시 결합한다.

```text
contract events
+ project events (선택)
+ fin claims
+ fin tax invoices
+ fin transactions
-> 공통 timeline DTO
-> 날짜/시간 정렬
-> 화면 표시
```

각 timeline item은 최소한 다음 메타정보를 가져야 한다.

- `source_type`: contract / project / finance
- `source_subtype`: claim / invoice / transaction / project_event 등
- `source_id`
- `occurred_at`
- `title`
- `summary`
- `contract_id`
- `project_id` (해당 시)
- `detail_url`

Finance 항목을 클릭하면 원본 Finance 상세 또는 해당 목록/모달로 이동하도록 한다.

## 11. 향후 확장 시 지켜야 할 원칙

1. 재무 사실은 Finance에서 한 번만 저장한다.
2. 계약/프로젝트 화면에서 필요하면 Finance 원본을 조회한다.
3. 계약은 Finance의 기본 연결축으로 유지한다.
4. 프로젝트는 분석 필요성이 있을 때 선택적으로 연결한다.
5. 귀속회사 축을 무시한 집계/조회 기능을 새로 만들지 않는다.
6. 화면 문자열을 업무 로직의 조건값으로 사용하지 않는다.
7. Excel import는 항상 preview와 검증 단계를 유지한다.
8. 실무 데이터 삭제는 soft delete를 기본으로 한다.
9. deployment에서 tenant 여부는 이름이나 active group만으로 판단하지 않고 tenant schema를 검증한다.
10. 새로운 도메인 데이터를 타임라인에 보이게 하기 위해 이벤트 테이블로 복제하지 말고, 가능한 경우 source 데이터를 통합 조회한다.
